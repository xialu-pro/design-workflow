# 功能检视器（PRD 关键流程 + 设计师检视清单走查）

面向华为计算生态产品团队，承接开发验收环节（功能侧）：开发完成、部署到测试环境后，按**体验设计师定义的功能检视清单**（主基准）走查关键流程，结合 DEMO 交互说明与 PRD 验收标准交叉校验，产出带证据的检视报告。

**业务背景**：鲲鹏、昇腾等计算生态产品，以及 openEuler（欧拉）、openGauss（高斯）、openUBMC 等开源项目。

## 运行模式：主对话 vs subagent

本 skill 有两种运行方式，流程一致，仅输入获取方式不同：

| 模式 | 触发方式 | 输入来源 |
|------|---------|---------|
| 交互模式（默认） | 用户直接调用 | 材料缺失时通过 AskUserQuestion 向用户索取 / 代填清单 |
| **subagent 模式** | design-workflow 以 Task 派发 | 所有输入（清单路径、DEMO 路径、PRD 路径、测试环境访问方式、已确认的用例清单）来自派发任务描述中的路径 |

**subagent 模式约束**：

1. 无法向用户提问——材料缺失时**在报告中声明缺失项并终止**，禁止猜测或臆测补位
2. 第 0 步前置校验（视觉 P0/P1 是否关闭）由编排层在派发前完成硬阻断——subagent 收到派发即视为已通过前置校验，无需自行读取 `Review_Visual_*`（保持与视觉检视的信息隔离，避免"顺杆爬"）
3. 第 1 步"向用户（或设计师）确认检视计划"由编排层在派发前完成（任务描述中的用例清单即已确认的计划）；用例化仍由 subagent 执行
4. 清单与 DEMO 冲突时（交互模式下的规则是询问设计师、禁止自行裁决）——subagent 无法询问，临时按清单为准执行（设计师是体验定义者），差异点记入报告"风险与建议"回传编排层，由编排层引导设计师确认

**项目级安装（推荐，随仓库分发，团队共享）**

```bash

cp -R <SKILL_SOURCE> .opencode/skills/  # OpenCode 原生
```

| 平台 | 全局路径 |
|------|---------|
| Claude Code | `~/.claude/skills/functional-reviewer/SKILL.md` |

## 检视基准模型（本 skill 核心）

功能检视的基准**由体验设计师定义，可结合 PRD，但不完全依赖 PRD**。基准按优先级排列：

| 优先级 | 基准来源 | 说明 |
|--------|---------|------|
| 1 | **设计师功能检视清单**（主基准） | 体验设计师定义的关键流程与体验检视点，含 PRD 未覆盖的体验细节（空态、反馈、异常路径、交互状态） |
| 2 | DEMO 交互说明 | 设计稿 HTML 中的交互注释与可操作行为——设计师意图的可执行表达 |
| 3 | PRD 验收标准（补充校验） | `docs/PRD_*.md` 第 4 章；提供功能编号可溯性（PRD-XXX），用于交叉校验防止清单漏项 |

**冲突裁决**：设计师清单与 PRD 冲突时以清单为准（设计师是体验定义者），但差异点记入报告"风险与建议"回传 PRD 修订；清单与 DEMO 冲突时询问设计师确认，禁止自行裁决。

**每条用例必须标注基准来源**（清单条目编号 / DEMO 模块 / PRD-XXX），报告概览中声明基准构成。

## 检视纲领

> 延续 design-draft-generator 对抗评审的精神，检视阶段同样强制遵守。

1. **证据先行**：每个判定（❌）必须有第一手证据——测试环境操作记录或截图；禁止凭记忆、凭开发描述、凭想象判定
2. **假设有偏**：检视者心态是"实现一定有缺陷，我的任务是找出来"；通过项也要有证据支撑，不允许"看起来没问题"式通过
3. **可溯可判**：每个问题定位到用例 + 差异点 + 基准来源；判定结论明确（✅/❌/⛔/➖），禁止模糊结论
4. **修复闭环**：❌ 问题修复后必须复检；全部关闭才宣告检视完成；无法修复项显式声明原因与风险

## 工作流程

### 第 0 步：输入判定（必先执行）

**前置校验**：确认视觉还原度检视已完成且 P0/P1 全部关闭（`reports/Review_Visual_*.md`）——未完成时先引导执行 visual-reviewer；用户明确要求跳过时在报告中声明"视觉检视未通过即开始功能检视"的风险。（subagent 模式下此校验由编排层在派发前完成，见"运行模式"）

| 材料 | 期望位置 | 缺失处理 |
|------|---------|---------|
| 设计师功能检视清单 | 填写模板（见 `templates/functional-checklist.md`）后随项目存放，推荐 `docs/FuncChecklist_[主题].md` | 将模板交给设计师填写；不便填写时按模板结构（流程名 / 关键步骤 / 预期体验 / 异常路径）通过 AskUserQuestion 代填；均不可得时降级为基准 2+3（DEMO 交互 + PRD），并在报告中声明"非清单基准" |
| DEMO 交付物 | `design/prototype_*.html`；路由 A 场景为 Pixso 设计稿，需用户描述关键交互 | 用于提取交互说明与降级基准 |
| PRD | `docs/PRD_[主题]_[YYYYMMDD].md` | 无 PRD 时仅作交叉校验缺失声明，不影响清单基准的检视 |
| 测试环境访问 | 测试环境 URL，或用户准备的操作结果截图材料包 | 按"第 2 步混合模式"判定获取方式 |

### 第 1 步：建立检视基准

1. **提取用例池**：以设计师清单为主体，从 DEMO 交互说明补齐清单未覆盖的可操作行为
2. **PRD 交叉校验（硬性动作）**：逐条比对 PRD 第 4 章每条验收标准与清单条目——语义被清单覆盖的可去重；**未被覆盖的必须补入用例池（标注基准来源 PRD-XXX），或在报告"风险与建议"中显式声明不采纳原因**；禁止静默遗漏
3. **用例化**：每条用例含——用例编号、优先级（P0/P1/P2，清单标注优先；未标注时按 PRD 优先级或询问设计师）、前置条件、操作步骤（明确到点击哪个入口、输入什么）、预期结果（引用基准原文：清单条目 / DEMO 注释 / PRD 验收标准）、基准来源
4. **输出检视计划**：用例清单 + 覆盖说明，向用户（或设计师）**确认后再执行**，禁止跳过确认直接开检

### 第 2 步：获取测试环境表现（混合模式）

- **优先实测**：测试环境 URL 可直接访问时，按用例逐步操作并记录实际结果与关键节点截图
- **降级材料**：测试环境需登录/内网/特定数据时，向用户明确索要材料清单——哪些用例的操作结果截图，每份注明对应用例编号；材料不完整时如实标记"未覆盖"，不得臆测补位
- **证据登记**：所有截图统一编号（如 `用例TC-003-02`），报告中的判定一律引用编号，禁止"如图"式无引用

### 第 3 步：逐条走查

按用例在测试环境实际操作，每条判定：

| 判定 | 含义 | 证据要求 |
|------|------|---------|
| ✅ 通过 | 实际结果符合预期 | 关键节点截图或操作记录 |
| ❌ 失败 | 与预期存在差异 | 截图 + 实际结果描述 + 与预期的差异点 |
| ⛔ 阻塞 | 无法执行（环境/数据/**依赖问题**） | 阻塞原因 + 责任归属（环境问题非开发问题，不计入失败） |
| ➖ 不适用 | 基准标注"本期不做"或超出本次检视范围 | 注明基准原文出处 |

**空洞通过护栏（禁止 vacuous pass）**：用例的前置状态由另一条已判 ❌ 的用例决定时（如异常路径依赖主路径先建立的筛选/编辑状态，而主路径功能未实现），该用例**禁止判 ✅**——功能缺失导致的"碰巧符合预期"不是正确性证据。此类用例判 ⛔ 并注明所依赖的问题编号，依赖问题修复后补测；⛔ 不计入通过率分母。

**覆盖要求**：

| 优先级 | 覆盖要求 |
|--------|---------|
| P0 | 主路径 + 异常路径 100% 覆盖 |
| P1 | 主路径 100% 覆盖，异常路径抽查 |
| P2 | 视情况抽查 |

**基准质量回传**：走查中发现 PRD 验收标准模糊不可测试（如"优化体验"类表述）或与设计师清单冲突时，记录为检视风险，检视完成后回传用户修订 PRD / 确认清单，避免下轮检视基准不清。

### 第 4 步：输出检视报告

输出到 `reports/` 目录（与 `docs/`、`design/` 并列），命名 `Review_Func_[主题]_[YYYYMMDD].md`，结构：

1. **概览**：用例总数（按优先级分列）、通过率、阻塞项数、基准构成声明（清单 / DEMO / PRD 各贡献多少条）
2. **功能检视用例表**：用例编号 → 步骤 → 预期（基准原文）vs 实际 → 判定（✅/❌/⛔/➖）→ 证据编号 → 基准来源
3. **问题清单**：❌ 项汇总（用例编号、差异点、修复建议）
4. **修复复检记录**：初始为空，随修复进度更新（见第 5 步）
5. **风险与建议**：PRD 与清单冲突项（回传修订）、验收标准模糊项、未覆盖项及原因

### 第 5 步：修复闭环

1. ❌ 问题清单交开发修复后，**只复检受影响的用例**（不重跑全量）
2. 复检结果更新进报告"修复复检记录"：每项标注 复检通过 ✅ / 仍有问题 ❌（附新证据）
3. **每次复检必须同步更新通过率终态**：报告概览区的通过率、❌/⛔ 统计须按最新一轮复检状态重算（⛔ 解除补测后重新计入分母）——终态是编排层判断"交付检视是否完成"的读取依据，仅追加复检记录而不更新通过率终态会导致误判
4. 全部 ❌ 关闭才宣告检视完成；无法修复项（如依赖外部系统、素材未就绪）在报告中显式声明原因与风险，由用户决策是否带问题上线
5. 检视完成时输出交付摘要：报告路径、通过率终态、遗留问题清单、基准修订建议（如有）

## 质量标准（检视前自查 + 报告评审基准）

1. **基准明确**：主基准为设计师清单；基准缺失时已显式声明并降级；每条用例标注基准来源
2. **计划先行**：用例清单经用户确认后才执行，禁止跳过
3. **证据完备**：所有 ❌ 判定附证据编号；通过项有记录可查；无空洞通过（依赖未实现功能的用例判 ⛔ 而非 ✅）
4. **覆盖达标**：P0 主路径 + 异常路径全覆盖；P1 主路径全覆盖
5. **闭环完整**：❌ 全部关闭或有显式风险声明；基准冲突与模糊项已回传
6. **冲突透明**：清单与 PRD 冲突项全部记录并回传，未自行裁决

## 与其他 skill 的关系

- **visual-reviewer**：姊妹 skill，视觉侧检视（测试环境 vs DEMO 还原度，P0/P1/P2 分级）；**检视顺序上本 skill 在其之后**——视觉 P0/P1 全部关闭（实现与 DEMO 一致）后再开始功能走查，避免视觉未对齐导致基准错位返工；两报告独立归档（`Review_Visual_*` / `Review_Func_*`）、独立闭环
- **design-draft-generator**：上游，其 DEMO 交付物是基准 2（交互说明）的来源，也是设计师清单的产生语境
- **requirement-doc-generator**：上游，其 PRD 是基准 3（交叉校验）的来源；检视中发现的验收标准模糊项与清单冲突项回传修订
- **design-workflow**：编排器，本 skill 是其阶段 4（交付检视）的功能路径执行者（subagent 派发），扮演角色"功能测试员"；也可独立使用，不强制经过该编排
