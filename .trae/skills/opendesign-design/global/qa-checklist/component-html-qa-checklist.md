## 📖 使用指南

### 如何使用本清单

```
1️⃣ 准备阶段：获取目标组件的 MD 设计规范文档
2️⃣ 提取阶段：从 MD 中提取所有设计参数（填入 §2 参数表）
3️⃣ 实现阶段：严格按照参数实现 HTML
4️⃣ 检查阶段：逐项勾选本清单（✅ 通过 / ❌ 不通过 / ⚠️ 需确认）
5️⃣ 验收阶段：交叉验证 + 浏览器测试
6️⃣ 归档阶段：保存检查记录 + 截图证据
```

### 检查结果标记说明
- ✅ **通过** - 完全符合规范
- ❌ **不通过** - 存在问题，必须修复
- ⚠️ **需确认** - 边界情况，需与设计师/产品确认
- ➖ **不适用** - 该项对当前组件无意义
- 📝 **备注** - 记录特殊处理或例外情况

## 🎨 三、视觉还原度检查

### 3.1 布局还原

- [ ] **尺寸精度**
  - [ ] 整体容器宽高符合规范
  - [ ] 内部元素比例正确
  - [ ] 🚨 **图片 / 整卡比例必须来自规范的固定比例集，禁止内容撑高**：凡规范规定固定比例的（如 OCard 封面 16:9 / 3:1；full-cover 的**整张卡片**也须保持该比例——宽按栅格定、高 = 宽 ÷ 比例），必须用 `aspect-ratio` 反推高度，禁止 `height` 写死值或让文字把容器撑高；同时反算内容层（padding + 标题行数 + 描述行数）在比例高度内放得下，禁止溢出
  - [ ] 间距使用正确的 Token 值（如 `gap: 8px` 对应 `gap-2`）
  - [ ] 无多余或缺失的空间

- [ ] **对齐方式**
  - [ ] 元素水平/垂直对齐方式正确
  - [ ] 文字基线对齐准确
  - [ ] Flexbox/Grid 布局参数正确
  - [ ] 🚨 **每个对齐值都能在 MD 规格表里找到对应行**（图标 vs 标题、文字 vs 图标、按钮 vs 容器）——查不到即规范缺项，禁止沿用默认值后静默继续
  - [ ] 🚨 **同一语义元素在所有布局变体下对齐口径一致**（如 OCard icon 的 vertical 与 horizontal 都必须「图标与标题顶对齐」）；发现变体间分裂即为缺陷
  - [ ] 🚨 **`align-items: center` 用于「小元素 vs 多行文字列」时必须复算**：center 的参照物是**整个文字列**（标题 + 间距 + 描述），不是标题单行——32px 图标 vs 82px 文字列居中会比标题低约 25px、掉到标题与描述之间。图标与标题顶对齐一律 `flex-start`
  - [ ] 🚨 **实测顶差而非只看 CSS**：对齐类问题肉眼易忽略，用 `getBoundingClientRect()` 量「图标.top − 标题.top」是否为 0（验收页实测标注脚本应内置该行）
  - [ ] 🚨 **变体结构与同类组件的同名变体镜像**：`vertical` = 视觉主体（封面 / 图标 / 头像）在文字**上方**，`horizontal` = 在文字**左侧**——生成前先查 MD 中该变体的 DOM 结构定义并照抄；禁止按个人理解另造结构（OCard icon 曾把 vertical 做成「图标与标题横排」，与 cover 的 vertical 逻辑相反，连带把「标题行盒→描述」撑成 10/14/8）

- [ ] **间距取值**
  - [ ] 🚨 **凡规范分档的间距，逐档核对**：把 MD 的 5 档分档表与实现的媒体查询逐档对照，禁止只验某一档就当全档通过（OCard icon 曾因只读「不分档」单值，窄档 padding 与间距全错）
  - [ ] 🚨 **容器 `gap` 与子元素 `margin` 是相加关系**：实测「A→B」= gap + margin，不等于其中任何一个。两个纵向间距值不同时禁用统一 gap（见 §10.2 #6）
  - [ ] 🚨 **margin 的参考点是「相邻盒子边界」，不是目标元素边界**：若 A 与某个比 A 高的兄弟 B 同处一个 flex 行，容器高 = `max(A, B)`，A 后面的 `margin-top` 实际从 **B 的底边**起算，间距会大出 `B − A`。实测「标题行盒→描述」时先确认标题没有被更高的图标/头像撑高父容器（OCard icon 曾实测 10/14/8 而非 8）
  - [ ] 🚨 **行盒口径 vs 字形口径要先对齐再量**：规范写「标题→描述 8px」时，先确认按 `line-height` 行盒量还是按字形视觉量，两者结果不同（行高大于字号时差值可达 4~6px）；OCard icon 已裁定为**行盒口径**

- [ ] **层级关系**
  - [ ] DOM 层级结构与 MD 中的树形图一致
  - [ ] 🚨 **可选 / 必选节点必须按规范标注输出**：规格表与结构树须逐节点标注「必选 / 非必选」；未标注时实现侧会把所有节点当必选全部输出（OCard full-cover 旧版未标图标槽与 Tag 的可选性，用户裁定二者均非必选、只有标题与正文必选）。核对每个实例的节点组合是否符合「可省略」的裁定
  - [ ] 🚨 **卡片内的子组件必须是组件实例，禁止宿主自绘样式**：卡片里出现 Tag / Button / 头像等语义时，本体必须调用对应组件（OTag / OButton…），样式归组件规范；禁止在宿主里自创 `.badge` / `.tag` 等同类语义样式（OCard 旧版 `.ocard__badge` 圆角 100px、padding 0 8px，与 tag.md 的 OTag 圆角 4px、内边距 6px 不符，违反 card.md 规则 4）
  - [ ] 🚨 **卡内数据统计行必须是 stats-bar 规格，禁止自创**：卡片里出现浏览 / 点赞 / 评论 / 收藏 / 评分等数据行时，类名（`.stats-bar`）、字号（`tip1` 14px / 行高 22px / 字重 400）、颜色（`--o-color-info3`）、间距（图标与文字 8px / 统计项之间 16px）、对齐（无评分居左；含评分评分居左、其余居右）全部按 card.md 规则 7 落地，禁止另起类名或改规格——统计栏是辅助信息区，字号固定降一档、不随卡片尺寸变化
  - [ ] 🚨 **同名子节点在多变体 / 多模式间必须同构**：同一子节点（如图标槽、Tag、Footer）在不同变体（cover / icon / full-cover）与不同模式（Light / Dark）下的样式定义必须一致，除非规范**显式**说明差异。❌ 规范内部自相矛盾（OCard 旧版 full-cover 图标槽写 `fill2` 底、icon 卡写 `primary1-light` 底，实现照 full-cover 执行后 Dark 下色块与卡片同色、整块消失）。生成前先通读规范中该节点的**全部**出现位置，逐处比对
  - [ ] 🚨 **Dark 模式必须是整套 Token 成对翻转，不是"只反色文字"（全局铁律）**：凡 `:root` 定义过、且在页面中被引用到的 Token，Dark 作用域（`.o-dark` 等）内必须逐项覆盖为 **Dark 值**——交互态（hover / active / selected / disabled）、组件自身色（背景 / 文字 / 边框 / 图标 / 阴影）、`*-light` 浅底一个都不能漏。❌ 只切 `info1` / `info3` / `fill2` 却漏掉 `primary*` 与 `*-light`；❌ 在 Dark 作用域给某元素单独写 Light 色值"修补"。**自检方法**：切主题后实测核对 ① hover / active / selected 三态颜色是否变化；② 组件背景 / 边框 / 图标色是否变化；③ `*-light` 浅底是否变化——任何一项"切了主题却没变"即违规。openEuler Dark 值真源 `opendesign-tokens/references/tokens-openeuler.md`（primary1 `rgb(73,122,248)` / primary2 `rgb(42,72,158)` / primary3 `rgb(29,51,120)` / primary1-light `rgb(18,34,87)`）。OCard 旧版只覆盖 fill/info/shadow，dark 区 hover 标题仍是 Light `#002FA7` 压在深色卡上，几乎不可见
  - [ ] z-index 层叠顺序正确（如有重叠元素）
  - [ ] 包含关系清晰（父容器 > 子元素）

## 🚫 十、常见陷阱与避坑指南

### 10.1 绝对不能犯的错误（❌ 致命级）

| # | 错误类型 | 错误示例 | 正确做法 | 后果 |
|---|---------|---------|---------|------|
| 1 | **禁用态颜色模拟** | 用 `filter: brightness(0.9)` 模拟 disabled | 使用精确的 RGB 值（如 `#84A1DC`） | 视觉不符合规范，无法通过验收 |
| 2 | **忽略官方资源** | 手写 SVG 或用 CSS 画图标 | 必须引用 `assets/` 目录下的官方文件 | 图标样式不一致，维护困难 |
| 3 | **遗漏交互状态** | 只实现了 Default 和 Selected | 必须实现全部 5 种状态（含 Disabled） | 功能不完整，用户体验差 |
| 4 | **单位错误** | 写成 `gap: 8rem` 而不是 `gap: 8px` | 严格对照 MD 的单位标注 | 布局完全错乱 |
| 5 | **Token 名拼写错误** | `color-primary1` 漏了 `--o-` 前缀 | 完整写法 `--o-color-primary1` | 样式不生效 |

### 10.2 容易出错的地方（⚠️ 警告级）

| # | 易错点 | 典型错误 | 检查方法 |
|---|-------|---------|---------|
| 1 | **间距不一致** | 有的地方 8px，有的地方 10px | 全局搜索 `gap\|margin\|padding` 统一检查 |
| 2 | **SVG 尺寸错误** | 设置为 `width="16"` 而非 `"24"` | 查看 MD 中的"SVG 文件尺寸"字段 |
| 3 | **Hover 效果过度** | 颜色变化太大或添加不必要的动画 | 保持微妙变化（brightness 1.1-1.2） |
| 4 | **禁用态可点击** | 忘记加 `pointer-events: none` | 检查 cursor 和事件绑定 |
| 5 | **移动端触摸区域太小** | 点击区域只有 16×16px | 最小 44×44px（Apple HIG 规范） |
| 6 | **统一 flex gap 与子元素 margin 叠加** | 容器 `gap: 16px` + 子元素 `margin-top: 8px`，实测间距 24px 而非 8px | 逐个量相邻子元素的 `top/bottom` 差；两个纵向间距值不同时改 `gap: 0` + 分段 margin |
| 7 | **对齐方式跨变体分裂** | vertical 用 `flex-start`、horizontal 用 `center`，同一图标在两种布局下高低不一 | 把 MD 规格表的「对齐方式」行逐变体对照；实测「图标.top − 标题.top」 |
| 8 | **分档规则写在基础规则之前** | 同特异性下被后部基础规则按源顺序反覆盖（如 ≤840 档 `margin: 4px` 被基础 `margin: 8px` 覆盖） | 分档媒体查询一律移到基础规则**之后**；逐档实测而非只看源码顺序 |
| 9 | **缩放子元素时漏看类名共用** | 类名被多个变体共用（如 `.ocard__icon` 同时服务 icon 卡与 full-cover 卡），全局改尺寸误伤其他变体 | 缩小作用域：`.变体类 .元素类` |
| 10 | **隐藏元素后仍读其尺寸** | footer 被 `display:none` 后实测脚本输出「描述→Footer盒顶 -200」等负数假值，误判为间距错误 | 读尺寸前加 `offsetParent` 守卫；`display:none` 也不解除 `:has()` 匹配 |
| 11 | **行高大于字号 → 视觉间距 ≠ margin** | 标题 `line-height: 30` / `font-size: 22`，margin 8px 实测字形视觉间距 ≠ 8px | 区分「**行盒间距**」与「字形视觉间距」两种口径，在 MD 规格表中写明按哪个量；OCard icon 已裁定为行盒口径（`desc.top − title.bottom`） |
| 12 | **兄弟元素比目标元素高 → margin 参考点被顶偏** | 标题在 `.ocard__header`（flex 行）内、描述是下一个兄弟节点。header 高 = `max(图标 32, 标题行盒 30)` = 32，比标题行盒底低 2px；desc 的 `margin-top: 8px` 从 **header 底**起算，实测「标题行盒→描述」= **10 / 14 / 8** 而非 8 | 把撑高兄弟的元素移出文档流：`.header { position: relative }` + `.icon { position: absolute; left: 0; top: 0 }` + `.title { padding-left: 图标宽 + 间距 }`。**不要**按档补偿 margin——标题折成 2 行后 header 高改由标题决定，补偿会变成过度、间距反而变小 |
| 13 | **量"盒子左边"当"文字起点"** | 标题用 `padding-left` 给图标让位后，`title.left` = header 左边，与图标右缘相减得出 −32 的假值，误判为重叠 | 量文字真实起点：`title.left + parseFloat(getComputedStyle(title).paddingLeft)` |
| 14 | **把未执行的测量当实测陈述** | 终端无输出 / 浏览器二进制缺失（`Executable doesn't exist`）时仍给出「实测」数值表 | 实测脚本一律「写文件 + Read 读文件」取结果；exit code 0 ≠ 有输出；浏览器不可用时显式标注「未做渲染实测」，禁止把推断当实测 |
| 15 | **变体结构与同类组件不镜像** | `vertical` / `horizontal` 是跨组件通用语义（主体在文字上方 / 左侧），实现侧按个人理解造结构：OCard icon 的 vertical 被做成「图标与标题横排」，与 cover 的 vertical（封面在上）逻辑相反 | 生成前查 MD 的变体 DOM 结构定义并照抄；核对 Header 方向（column / row）与图标是否移出 Header；镜像同类组件同名变体 |
| 16 | **固定比例的容器被内容撑高** | 规范规定图片 / 整卡保持 16:9 / 3:1，实现侧漏写 `aspect-ratio`，容器高度由文字内容决定，卡片随文案长短漂移、同行底边参差 | 比例容器一律 `aspect-ratio` 反推高度（宽由栅格定）；禁止 `height` 写死；反算内容层在比例高度内放得下（OCard full-cover 最窄档 264px 卡 → 16:9 高 148.5px ≥ 内容层 140px，实测余量 8.5px） |
| 17 | **卡片内 Tag 用自创样式而非 OTag 组件** | 宿主自己画徽标（如 OCard 旧版 `.ocard__badge`：圆角 100px / padding 0 8px），与 tag.md 的 OTag（圆角 4px / 水平内边距 6px / small 高 20px）不符，且违反宿主规范自己的「必须调用组件」条款 | 卡片内 Tag / Button 一律调组件类名（`.otag` / `.o-button`），样式独立成块并逐项对齐组件规范；生成前先查宿主规范是否已有「必须调用 XX 组件」条款 |
| 18 | **可选节点未标注 → 被当成必选全部输出** | 结构树把可选节点与必选节点并列书写、不标「可选」，实现侧把图标 / Tag / Footer 全部输出，用户要删时才发现规范从没说过能删 | 规格表与结构树逐节点标注「必选 / 非必选」；生成实例时按需裁剪节点组合，并用多个实例分别演示不同节点组合 |
| 19 | **Dark 模式只切文字色，交互态 / 组件色仍是 Light 值** | 把 Dark 理解成"反色文字"，`.o-dark` 只覆盖 `info1` / `info3` / `fill2` / `shadow`，`primary*` 与 `*-light` 没切——dark 区 hover 标题仍是 Light 深蓝压在深色卡上（对比度极低、几乎不可见），按钮 hover、图标槽底色、Tag 底色同样全是 Light 值 | Dark 是**整套 Token 成对翻转**（hard-constraints §0.1 铁律）：业务规则只写 `var(--o-color-*)`，Dark 作用域逐项覆盖变量为 Dark 值；切主题后实测 hover / active / selected 三态、组件背景 / 边框 / 图标、`*-light` 浅底是否都变化 |

### 10.3 最佳实践建议（💡 优化级）

### 11.1 权重分配

| 检查类别 | 权重 | 说明 |

| **三、视觉还原度** | 20% | 最直观的质量体现 |
| **四、交互行为** | 15% | 功能性和可用性 |
| **五、可访问性** | 5% | 合规性和包容性 |
| **六、响应式兼容** | 10% | 多端适配能力 |
| **七、代码质量** | 10% | 可维护性和扩展性 |
| **八、性能体验** | 5% | 加载速度和流畅度 |
| **九、测试验收** | 5% | 验证充分性 |
| **总计** | **100%** | |

### 11.2 评级标准

| 等级 | 分数范围 | 含义 | 处理方式 |
|------|---------|------|---------|
| 🏆 **S 级** | 95-100 | 完美实现，可直接发布 | 作为范例推广 |
| ✅ **A 级** | 85-94 | 优秀，微小瑕疵可接受 | 修复后发布 |
| 👍 **B 级** | 75-84 | 良好，存在少量问题 | 必须修复后再发布 |
| ⚠️ **C 级** | 60-74 | 及格但需大幅改进 | 返工重做重点模块 |
| ❌ **D 级** | < 60 | 不合格 | 全面返工 |

### 11.3 一票否决项

出现以下任一情况，**直接判定为不合格（D 级）**：

- ❌ 禁用态颜色使用 CSS filter 模拟而非精确值
- ❌ 未使用官方资源文件（手绘图标/SVG）
- ❌ 缺少超过 30% 的必需交互状态
- ❌ 存在 JavaScript 运行时报错
- ❌ 在主流浏览器中无法正常显示
- ❌ 安全漏洞（XSS、注入攻击等）
