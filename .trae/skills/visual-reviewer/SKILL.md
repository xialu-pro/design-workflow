# 视觉还原度检视器（测试环境 vs DEMO 交付）

面向华为计算生态产品团队，承接设计稿交付之后的开发验收环节（视觉侧）：开发完成、部署到测试环境后，比对测试环境页面与 DEMO 交付物的视觉一致性，产出带证据、分级的检视报告。

**业务背景**：鲲鹏、昇腾等计算生态产品，以及 openEuler（欧拉）、openGauss（高斯）、openUBMC 等开源项目。

## 运行模式：主对话 vs subagent

本 skill 有两种运行方式，流程一致，仅输入获取方式不同：

| 模式 | 触发方式 | 输入来源 |
|------|---------|---------|
| 交互模式（默认） | 用户直接调用 | 材料缺失时通过 AskUserQuestion 向用户索取 |
| **subagent 模式** | design-workflow 以 Task 派发 | 所有输入（DEMO 路径、测试环境访问方式、已确认的检视页面清单）来自派发任务描述中的路径 |

**subagent 模式约束**：无法向用户提问——材料缺失时**在报告中声明缺失项并终止**，禁止猜测或臆测补位；第 1 步"向用户确认检视计划"由编排层在派发前完成（任务描述中的页面清单即已确认的计划），subagent 直接从第 2 步开始执行。

## 安装方式

本 skill 遵循 Agent Skills 开放标准（一个目录 + 一个 SKILL.md），支持 Claude Code、OpenCode、Codex 主流 AI 编程平台。`<SKILL_SOURCE>` 指本 skill 目录（含 SKILL.md 的 `visual-reviewer/` 文件夹）。

**项目级安装（推荐，随仓库分发，团队共享）**

```bash
# 在项目根目录执行，按所用平台复制到对应目录
cp -R <SKILL_SOURCE> .claude/skills/    # Claude Code
cp -R <SKILL_SOURCE> .opencode/skills/  # OpenCode 原生
cp -R <SKILL_SOURCE> .agents/skills/    # Codex（OpenCode 亦兼容此路径）
```

**全局安装（本机所有项目生效）**

| 平台 | 全局路径 |
|------|---------|
| Claude Code | `~/.claude/skills/visual-reviewer/SKILL.md` |
| OpenCode | `~/.config/opencode/skills/visual-reviewer/SKILL.md`（兼容 `~/.claude/skills/`、`~/.agents/skills/`） |
| Codex | `~/.codex/skills/visual-reviewer/SKILL.md`（新版亦支持 `~/.agents/skills/`） |

**注意**：目录名必须与 frontmatter `name` 一致（`visual-reviewer`）；修改后未生效时重启对应 CLI。

## 检视纲领

> 延续 design-draft-generator 对抗评审的精神，检视阶段同样强制遵守。

1. **证据先行**：每个判定（❌/P0/P1）必须有第一手证据——测试环境截图或样式/DOM 比对记录；禁止凭记忆、凭开发描述、凭想象判定
2. **假设有偏**：检视者心态是"实现一定有偏差，我的任务是找出来"；通过项也要有证据支撑，不允许"看起来没问题"式通过
3. **可溯可判**：每个问题定位到页面 + 位置 + 对应的 DEMO 模块；判定分级明确，禁止模糊结论
4. **修复闭环**：P0/P1 问题修复后必须复检；全部 P0/P1 关闭才宣告检视完成；无法修复项显式声明原因与风险

## 工作流程

### 第 0 步：输入判定（必先执行）

检视需要两样材料，缺失时按对应方式处理，禁止材料不全就开跑：

| 材料 | 期望位置 | 缺失处理 |
|------|---------|---------|
| DEMO 交付物（比对基准） | `design/prototype_*.html`；路由 A 场景为 Pixso 设计稿，需用户提供导出截图 | **必须先补齐视觉基准**（向用户索取 Pixso 导出截图或其他确认的基准）；仍无法提供则检视阻塞，由用户决策，不得无基准开检 |
| 测试环境访问 | 测试环境 URL，或用户准备的截图材料包 | 按"第 2 步混合模式"判定获取方式 |

PRD 非本 skill 必需材料；涉及适配范围核对时可参考 `docs/PRD_*.md` 第 3.2 节。

### 第 1 步：建立检视基准

1. 从 DEMO 提取页面/楼层序列，形成检视页面清单
2. 输出检视计划（页面清单 + 访问方式），向用户**确认后再执行**，禁止跳过确认直接开检

### 第 2 步：获取测试环境表现（混合模式）

- **优先实测**：测试环境 URL 可直接访问时，通过浏览器逐页打开，按 DEMO 同尺寸/同断点截图
- **降级材料**：测试环境需登录/内网/特定数据时，向用户明确索要材料清单——哪些页面的截图，每份注明对应页面编号；材料不完整时如实标记"未覆盖"，不得臆测补位（subagent 模式下无法索要：任务描述未附材料包时在报告中声明"测试环境表现缺失"并终止）
- **证据登记**：所有截图统一编号（如 `页面A-01`），报告中的判定一律引用编号，禁止"如图"式无引用

### 第 3 步：逐页逐维度比对

按下表 7 个维度检查，每个维度给出结论 + 证据：

| # | 维度 | 检查要点 |
|---|------|---------|
| 1 | 布局结构 | 楼层顺序与 DEMO 一致；栅格/分栏无误；响应式断点行为一致 |
| 2 | 组件规格 | 组件类型与 DEMO 一致（按钮/卡片/表格/标签/代码块）；hover/选中/禁用等状态齐全 |
| 3 | 间距节奏 | 模块间距、组内间距的层级关系保持（组内 < 组间）；4/8 倍数节奏未被破坏 |
| 4 | 字号层级 | 字号阶梯 ≤ 4 级；层级对比清晰，无"看起来差不多"的模糊层级 |
| 5 | 色彩 | 品牌色/状态色与 DEMO 一致；正文对比度 ≥ 4.5:1（WCAG AA） |
| 6 | 图标与图片 | 图标语义一致；**深色/品牌色背景上图标必须为白色，禁止黑色图标直出**（历史高频问题，优先检查） |
| 7 | 视觉细节 | 导航 Logo 与文字垂直居中（禁止贴底 hack）；对齐线贯通；按钮/操作元素无截断（历史高频问题，优先检查） |

每个差异按下表定级，禁止跳过定级直接报"不一致"：

| 级别 | 定义 | 示例 | 处理要求 |
|------|------|------|---------|
| **P0 阻断** | 结构/功能级不一致 | 楼层缺失或顺序错乱、功能入口缺失、布局错位、深色背景黑色图标 | 必须修复 |
| **P1 偏差** | 目视可辨的规格不一致 | 间距/字号/色值明显偏差、交互状态缺失、对齐问题、按钮/元素截断 | 必须修复 |
| **P2 容忍** | 合理实现差异 | 亚像素差异、字体渲染差异、滚动条样式、DEMO 中标注占位的素材差异 | 记录备忘，不要求修复 |

### 第 4 步：输出检视报告

输出到 `reports/` 目录（与 `docs/`、`design/` 并列），命名 `Review_Visual_[主题]_[YYYYMMDD].md`，结构：

1. **概览**：检视范围（页面清单）、测试环境与访问方式（实测/材料）、问题统计（P0/P1/P2 数量）
2. **逐页检视表**：页面 → 维度（7 维度）→ 差异描述 → P 级 → 证据编号 → 修复建议（改什么、怎么改）
3. **问题清单**：P0/P1 汇总（页面、位置、描述、修复建议、对应 DEMO 模块）；P2 备忘列表（不要求修复）
4. **修复复检记录**：初始为空，随修复进度更新（见第 5 步）
5. **风险与声明**：未覆盖项及原因、无法修复项的原因与风险

### 第 5 步：修复闭环

1. P0/P1 问题清单交开发修复后，**只复检受影响的页面**（不重跑全量）
2. 复检结果更新进报告"修复复检记录"：每项标注 复检通过 ✅ / 仍有问题 ❌（附新证据）
3. **每次复检必须同步更新终态小节**：P0/P1 的关闭计数（如"P0 1/1 已关闭，P1 7/7 已关闭"）与放行结论（"是否可进入功能检视"）——终态是 functional-reviewer 前置校验与编排层硬阻断的读取依据，仅追加复检证据而不更新终态会导致阻断误判
4. 全部 P0/P1 关闭才宣告检视完成；无法修复项在报告中显式声明原因与风险，由用户决策是否带问题上线
5. 检视完成时输出交付摘要：报告路径、问题终态、遗留问题清单

## 质量标准（检视前自查 + 报告评审基准）

1. **基准明确**：必有 DEMO 基准（缺失即阻塞），检视不无基准开跑
2. **计划先行**：检视页面清单经用户确认后才执行，禁止跳过
3. **证据完备**：所有 ❌/P0/P1 判定附证据编号；通过项有记录可查
4. **分级客观**：差异按 P0/P1/P2 定级且定级依据可解释；无"整体还行"式模糊结论
5. **闭环完整**：P0/P1 全部关闭或有显式风险声明
6. **高频问题优先**：深色背景图标颜色、导航垂直居中、元素截断三类历史高频问题必查

## 与其他 skill 的关系

- **design-draft-generator**：上游，其 DEMO 交付物是本 skill 的比对基准（路由 B 为 `design/` HTML 原型可直接打开比对；路由 A 为 Pixso 设计稿，需用户导出截图作为基准）
- **functional-reviewer**：姊妹 skill，功能侧检视（设计师清单主基准的关键流程走查）；**检视顺序上本 skill 在前**——本 skill 的 P0/P1 全部关闭（实现与 DEMO 一致）后再进入功能检视，避免视觉未对齐导致功能基准错位返工；两报告独立归档（`Review_Visual_*` / `Review_Func_*`）、独立闭环
- **design-workflow**：编排器，本 skill 是其阶段 4（交付检视）的视觉路径执行者（subagent 派发），扮演角色"视觉一致性测试员"；也可独立使用，不强制经过该编排
